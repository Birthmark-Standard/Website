Privacy Design

How the Birthmark Standard protects photographer privacy while enabling verification

The Principle: Never Build the Map

A provenance system has to show that content came from a registered device. In an ordinary design, whoever checks the device and records the content can link the two, and that link is a map of who photographed what. Data breaches are now routine, so protecting such a map isn't enough.

The Birthmark Protocol never builds the map. The facts that would link a device to its content are held by different, independently operated components, and each holds only what its own job requires. We call this property Semantic Non-Assembly: for each component, we ask whether an attacker holding everything that component holds, keys included, could link a device to a picture. The answer is designed to be no.

This is a property of the architecture, not a policy. A rule that says "don't combine this data" can be broken by an insider. A system where no single component ever holds the data needed to combine is harder to betray.

Four Pillars of Privacy and Integrity

1. Two Separate Channels

Every submission is split into two channels that travel on separate network paths, through relays run by different operators, to different servers.

  • Content channel: The image fingerprint and optional fields, sent to two content channel servers. It carries no credential.
  • Credential channel: The device's encrypted credential, sent to the credential channel server and from there to the manufacturer's validator. It carries no image fingerprint.

The channels are joined only by the Full Packet Hash. The validator receives it only in encrypted form, under a single-use key it never holds, so it can confirm a device and sign a verdict without being able to tell what the device photographed. Only the first relay on each path sees the device's network address, and it can't read the packet or tell which channel it belongs to.

2. No Single Point of Exposure

We tested each component in turn by giving an attacker all of its keys and everything it sees. Machine-checked proofs (using the ProVerif protocol verifier) show that none of the following, compromised on its own, can link a device to a picture:

  • The credential channel server
  • The manufacturer's validator
  • A gatekeeper
  • A content channel server
  • A first relay
  • A public observer of the registry

One nuance applies to the validator: it issues each submission's Modification Verdict, and verdicts are public. A rare verdict narrows the set of records it could belong to. Decoy submissions carry verdicts drawn from the same mix as real ones to blunt this.

What it would take to link a device to a picture: compromising the validator together with the credential channel server, or the validator together with a gatekeeper. These are components in different roles, which the system requires to be run by organizations that share no ownership, jurisdiction, administrative control, logs or keys. Such a coordinated compromise defeats the guarantee, and the consortium's independence rules, removal process and audits exist to prevent it.

Bulk surveillance stays hard: Because no component holds images, every attempt to link a device to a picture has to start from a specific image already in hand. No one can browse the registry to enumerate photographers.

3. No Single Party Can Forge a Record

Several independent checks stand between a submission and the registry:

  • The manufacturer's validator signs each verdict, and the token binding stops the credential channel server from attaching a genuine credential to a submission the device never made.
  • Three independent gatekeepers each check the signatures and post to their own match board. A content server proceeds only when two of the three boards agree.
  • The registry writes a record only when two content servers, run by different operators, submit matching signed entries.

What this means: Machine-checked proofs show that one compromised content server can't make the registry write or alter a record, and that even two of the three gatekeepers working together can't force a record the validator never approved.

4. Records Live Outside the File

The metadata problem: Social media platforms routinely strip EXIF metadata and embedded signatures through compression and format conversion. Credentials stored in the file, such as C2PA Content Credentials, are lost along with them.

How Birthmark differs: The record is kept in the registry, not in the file, so it can't be stripped away. Anyone holding an exact copy of the registered file can find its record.

The trade-off: Matching is exact. Any change to the file outside certified editing software, including recompression, resizing, metadata removal or a screenshot, produces a new file with no record. Edits made in certified software create a new record that links back to the original.

Complementary to C2PA: C2PA carries rich metadata and edit history while the file stays intact. Birthmark keeps an independent record that doesn't depend on the file's metadata surviving.

Additional Privacy Mechanisms

Beyond these four pillars, the system includes additional privacy protections:

Hash-Only Storage

Image content is never transmitted to any server or stored anywhere. Only SHA-256 hashes reach the registry, and a hash can't be reversed into the image.

Timing Protection

Every stage holds messages for a random time, every network leg is padded to a size within a common range, and sixty decoy transactions are in flight at all times, each producing a record indistinguishable from a real one. Registry timestamps reflect a coarsened posting time, not the capture time. In simulation, no single compromised component identified the originating device measurably more often than an outside observer holding no keys.

Metadata Hashing (Optional)

A device can include a hash covering the capture time, location and, optionally, the owner. Each field is salted with its own random value stored in the image file, so a photographer can later prove one field without revealing the others. Because the salts differ, the hash doesn't link one photographer's records together.

Discard and Audit

The values that connect the two channels (the random number, the single-use key and the signed intermediate values) are discarded as soon as each check succeeds, and first relays discard routing information after forwarding. A photographer can ask the consortium to search the logs of every server that handled one of their past submissions for any retained copy. A retained copy is a governance violation, handled through the removal process.

Resistance to Legal Compulsion

A consortium member compelled to violate the governance charter is removed from the network. The compelled operator faces a public choice: resist the order and stay, or comply and be removed. Either outcome is visible in the audit record, which turns silent pressure into a visible governance event. A compelled single component still yields only the fragment shown in the table above.

Limits and What This System Does NOT Protect Against

  • Staged scenes: A real camera can photograph a fake scene.
  • Screen photos: A camera can register a photo of a screen, print or projection showing an AI-generated image.
  • Metadata leakage by the user: If you share your image with its original EXIF data, that data is no longer private.
  • Coordinated compromise across roles: A validator compromised together with the credential channel server, or with a gatekeeper, can link a device to a picture. Independence requirements and governance exist to prevent this, but they are not cryptographic guarantees.
  • Anonymity depends on the manufacturer: The credential channel server learns which group of devices a submission comes from, so a manufacturer with few registered devices offers a smaller crowd to hide in.
  • Edits are software-attested: Edit records rest on the editing software and its developer's judgment, not on camera hardware.
  • Timing analysis is tested, not proved: Resistance to timing and traffic analysis comes from simulation. Even a passive outside observer guesses the device several times better than chance, and active attacks (delaying or dropping traffic) have not yet been evaluated.
  • Network visibility: First relays see the device's network address, and the validator sees the credential on every transaction.
  • Positive verification only: Images from manufacturers that don't take part have no record, so a missing record proves nothing.

Design Philosophy: The Birthmark Standard proves an image came from a registered capture device, not AI generation. It does not prove the scene is real, only that a physical device captured it. Truth verification still requires journalistic judgment and context.
