Technical Architecture

How a photograph's fingerprint travels from the camera to a permanent public record, without any single server learning which camera took it.

The Parts of the System

The Birthmark Protocol splits the job of authenticating a photo across independently operated components. Each one holds only what its own task requires.

  • Capture device: The camera, or a capture app on a phone. It fingerprints the image file and sends two separate messages: one about the content and one carrying its credential.
  • Relays: Forward encrypted packets they cannot read. Only the first relay on each path sees the device's network address.
  • Credential channel server (C): Receives the credential message, asks the manufacturer for a verdict, and passes the approved result to the gatekeepers.
  • Credential validator: Run by the camera manufacturer (or, for edits, by the editing software's developer). Confirms the credential belongs to a registered device. It never sees the image fingerprint.
  • Gatekeepers and match boards (three of each): Each gatekeeper independently checks the signatures on an approval and posts it to its own match board.
  • Content channel servers (F and I): Each receives the content message directly from the device, waits until two of the three match boards confirm an approval, and submits an entry to the registry.
  • Birthmark Media Registry: A consortium blockchain that writes a record only when F and I submit matching entries, and answers public lookups.

The relays, C, the gatekeepers, F and I all run on Registry Nodes, the servers operated by consortium members. Credential validators are not Registry Nodes: manufacturers and software developers run them, outside consortium governance.

1. On the Device: Capture and Packet Creation

When you press the shutter, the device fingerprints the saved file and builds three encrypted packets. It never sends the image itself.

Hardware Root of Trust

Every camera sensor has tiny manufacturing variations, recorded at the factory in a Non-Uniformity Correction (NUC) map. A camera's credential is a hash of this map, measured and stored at manufacture. The manufacturer's validator keeps a list of registered credentials, and checking against that list is the only way a device is authenticated. The device holds no signing key and signs nothing.

For phones, the credential must be provisioned into hardware-backed storage and recognized by the validator. The exact mechanism for phones is still being specified.

The credential works like a secret password. If someone physically extracts it from a device, they could use it until the manufacturer revokes it, so revocation is the remedy for a compromised device. Extraction attacks are costly and affect one device at a time.

What Happens at Capture

The device saves the image file, including its EXIF block, and then computes a SHA-256 hash of the whole file as stored. This hash is the image's fingerprint, called the ContentHash. If a capture produces more than one image (for example a RAW file and a processed JPEG), each one is registered as its own transaction.

The device also draws a random, single-use 128-bit number for this transaction. It combines the ContentHash, that number and any optional fields into a second hash, the Full Packet Hash. The Full Packet Hash is the only value the two channels share, and because the random number is never published, it cannot be traced back to a registry record later.

Optional metadata: The device can include a Capture Metadata Hash covering the capture time, location and (optionally) owner. Each field is salted with its own random value, stored in the image file, so the photographer can later reveal one field without revealing the others. The hash fixes what the device recorded at capture. It does not prove that the device's clock or GPS reading was correct.

The Credential Packet

The device builds a token that only its manufacturer's validator can decrypt. The token contains the device credential, a single-use number for detecting replays, the Processing Claim (zero for an unedited capture), and a binding hash that ties the token to this one submission.

The token goes into the credential packet along with a key reference (which tells the validator which key and member list to use), the Full Packet Hash, and a single-use key generated for this transaction. The whole packet is encrypted for C. C can read the Full Packet Hash but not the token.

The Content Packets

The device builds two copies of the content packet, one encrypted for content channel server F and one for I. Each contains the ContentHash, the random number, and any optional fields (the metadata hash and, for an edit, the original image's ContentHash). The content packets carry no credential and no verdict.

Delivery

The three packets travel on three separate paths, each through a first relay and a second relay. The device picks its routes from a routing table distributed to every device. The first relays on the three paths are run by three different operators, and are located outside the jurisdiction the photographer works in, because they are the only servers that see the device's network address.

A first relay cannot read the packet, cannot tell whether it is a credential packet or a content packet, and cannot tell which server it is headed to, because each destination's key is disguised differently on each line of the routing table. C, F and I are also run by three different operators.

Before sending, the device holds each packet for a random time and pads it to a random size within a common range, so packets can't be told apart by size or timing.

2. Birthmark Infrastructure: Validation and Registry Posting

The two channels are checked separately and joined only by the Full Packet Hash. No server ever receives the image.

Credential Channel Server

C opens the credential packet. It can read the Full Packet Hash and the single-use key, but not the token. C encrypts the Full Packet Hash under the single-use key and forwards the result, together with the still-encrypted token, to the validator named by the key reference. The validator never receives the single-use key, so it can't read the Full Packet Hash.

Credential Validator

The validator decrypts the token and makes three checks: the credential is on its list of registered devices, the token's binding hash matches the encrypted Full Packet Hash that C sent, and the replay number hasn't been used before. The binding check stops a compromised C from attaching a genuine token to a submission the device never made.

If all three checks pass, the validator reads the device's Processing Claim and issues the Modification Verdict, which describes how the image was processed (see section 3). It signs the verdict together with the still-encrypted Full Packet Hash, using a ring signature that shows a registered validator signed without showing which one. If a check fails, the validator sends back a rejection. A verdict that flags edits is still a record, not a rejection.

The validator learns which device is checking in, but never what it photographed. Its database answers one question only: is this credential registered? Before connecting to the network, each validator's database design is inspected by an independent auditor, and that attestation is posted to the registry.

Gatekeepers and Match Boards

C checks the validator's signature, adds its own ring signature over the Full Packet Hash and the verdict, and sends the result to three independent gatekeepers. Each gatekeeper checks both signatures, countersigns, waits a random time, and posts to its own match board. The ring signatures mean a gatekeeper can't tell which validator approved the submission or which server acted as C.

Content Channel Servers and the Registry

F and I each receive the content packet directly from the device and recompute the Full Packet Hash. Each waits until the same Full Packet Hash and verdict appear, with valid signatures, on at least two of the three match boards. Then each submits a signed entry to the registry.

The registry writes a record only when it receives two matching entries signed by two different servers. This dual approval means one compromised content server can't create or alter a record on its own. Two colluding gatekeepers can't force one either, because they can't produce C's signature over an approval C never issued. If a record for the same ContentHash already exists, a new submission is matched to the existing record and doesn't create a second, later one.

After their checks, the servers discard the random number, the single-use key and the signed intermediate values. An audit process lets a photographer, the only person who holds the random number, ask the consortium to check that nothing was kept.

What Gets Stored in the Registry

A finalized record for a capture is 42 bytes:

  • ContentHash (32 bytes): the image fingerprint
  • Modification Verdict (1 byte): how the image was processed
  • Optional-field flags (1 byte): which optional fields are present
  • Posting timestamp (8 bytes): when the record was posted, coarsened for privacy. This is not the capture time.
  • Optional: the Capture Metadata Hash and, for an edit, the original's ContentHash (32 bytes each, up to 106 bytes total)

The record contains no device identifier, no manufacturer identifier, no signatures, and does not name the servers that submitted it.

The registry is a permissioned consortium blockchain built on the Substrate framework, with no cryptocurrency. Finality uses GRANDPA consensus, which requires 67% agreement among Registry Nodes. A blockchain is used rather than a simple append-only log because removing a record would require compelling a supermajority of independent organizations across different jurisdictions at once.

Timing and Decoys

Every stage holds messages for a random time before passing them on, and every network leg is padded to a size within a common range. Content packets and the content servers' checks wait longer than other stages, which simulation showed was the most important setting for resisting timing analysis. Sixty decoy transactions are in flight at all times, each producing a record indistinguishable from a real one, and the registry commits records in batches.

The cost is time. In simulation, the average time from capture to a finalized record is about 17 minutes, so photographers should expect a record to appear on that scale, not instantly.

3. Edited Images

An edited image is a new file with a new fingerprint. It enters the system as a new transaction that points back to the original.

Certified Media Processing Software

Edits are registered by Certified Media Processing Software (CMPS): an editing application with its own checker, or a checker that works alongside another editor. The CMPS takes the device's place, and the software developer's server takes the validator's place. The edit is a new submission with the software's own credential, so it never reuses the camera's credential.

The original image's ContentHash travels only in the content channel, never with the credential, so the developer's validator can't link the user to the original image.

The Processing Claim and Deviation Score

The CMPS records every tool applied and at what intensity. When the edit is saved, it replays those tools on randomly chosen patches of the original image and compares the predicted result with the same patches of the saved image. The cumulative mismatch is the Deviation Score. A tool that changes content in ways its settings don't describe produces a large mismatch. Patch locations are chosen unpredictably, after the edits are final, so an edit can't be hidden outside them.

The CMPS sends the classes of tools it applied and the Deviation Score as its Processing Claim. Tools that add or change content, such as cloning, healing or generative fill, can't be replayed. They are declared by their tool class and left out of the Deviation Score.

The Modification Verdict

The developer's validator turns the claim into a one-byte Modification Verdict:

  • Five tool-class flags: tone and colour; detail; geometry; content removal, insertion or alteration (including generative tools); and compositing. These flags accumulate along a chain of edits.
  • An undeclared-change flag: set when the Deviation Score exceeds the validator's threshold and no content-changing tool was declared.
  • A deviation level: one of four classes. The software developer sets where each class begins, because they know their own tools.

An unedited capture has a verdict of zero. The protocol guarantees the verdict isn't altered on its way to the registry, but it does not check whether the validator's judgment was correct. Anyone who holds both images and the developer's published rules can rerun the check.

Trust Level

Edit authentication is software-attested, not hardware-anchored, so it is weaker than the guarantee for an original capture. The software's credential is registered using platform attestation, which raises the cost of registering credentials in bulk but can't prove what a modified client did. Edits made outside certified software (including a platform's own recompression) produce a new file with no record.

4. Public Verification: Anyone Can Verify

Once a record is in the registry, anyone can check an image. No account, subscription or intermediary is required.

How Verification Works

A verifier computes the SHA-256 hash of the image file locally and asks the registry whether it holds a record for that hash. If it does, the registry returns the record: the Modification Verdict, the coarsened posting time, and any optional fields such as the original's ContentHash for an edit.

A match shows that the file came from a registered device. A non-match proves nothing: the image may come from a manufacturer that doesn't take part, or may have been changed since it was registered.

The registry deliberately does not support reverse lookup, attribution search or photographer enumeration. You can ask whether an image came from a registered device, but the registry holds nothing that would answer which one.

Exact Matching

Matching is exact. The copy you check must be byte-for-byte identical to the registered file. Any change outside certified software, including recompression, resizing, metadata removal or a screenshot, produces a different hash with no record. The record itself can never be stripped away, because it lives in the registry and not in the file.

This is a deliberate trade-off. A perceptual hash would tolerate small changes, but it would also treat visually similar images as the same, which is exactly what an attacker substituting a near-copy would exploit.

Tracing Edit Chains

Each edited version's record carries its original's ContentHash. If you hold only the edited image, you can read that field and look up the original's record. If you hold both images, you can hash each one and confirm that the edited record points to the original. No record in the chain carries a device identifier.

What It Does Not Prove

The system verifies hardware origin, not truth. A staged scene passes verification, as does a photograph of a screen, print or projection. Judging what an image shows still requires journalistic judgment and context.
